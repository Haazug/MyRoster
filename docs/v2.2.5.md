# MyRoster v2.2.5 — Web Push

This release adds optional scheduled-flight push notifications, a per-device preference panel at `/profile#notifications`, native permission requests, a test notification, service worker reception/click handling, authenticated subscription management, server dispatch and Supabase SQL. It preserves v2.2.4 scheduling, imports, live discovery, alliances and display typography.

**Code alone does not activate push.** Apply the database migration, configure the hosting environment and enable the scheduler below. The interface distinguishes unavailable server setup from a registered device and a scheduler with a recent successful run. Local status calculations and calendar exports continue to work without push.

## 1. Supabase tables

Run [`supabase/migrations/202611010001_push_notifications.sql`](../supabase/migrations/202611010001_push_notifications.sql) in Supabase's SQL Editor. It can be rerun. It uses the existing `public.user_data` bookings collection and `auth.users`.

Tables and the claim function are service-role only. Browser requests use the existing Supabase access token; server endpoints verify it with `auth.getUser` and scope subscription operations to that user. Encryption keys and endpoint URLs are stored in `push_subscriptions`, not shared profile data.

The migration shared in the conversation is this same schema/function. No production SQL was executed from the development environment.

## 2. Hosting environment (for example Vercel)

Use the existing production project; keep its current variables. Add these as **server environment variables**, never in browser code or Git:

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Existing Supabase project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase service-role key, server only |
| `WEB_PUSH_VAPID_PUBLIC_KEY` | Public key from the command below |
| `WEB_PUSH_VAPID_PRIVATE_KEY` | Matching private key, server only |
| `WEB_PUSH_VAPID_SUBJECT` | `mailto:` followed by a valid operator contact email, or a valid HTTPS contact URL |
| `PUSH_CRON_SECRET` | A long random secret, identical to the scheduler's Vault token |

The existing client also needs `NEXT_PUBLIC_SUPABASE_ANON_KEY` as before.

Generate a stable VAPID pair on a trusted machine:

```sh
npm run push:keys
```

Generate the cron secret:

```sh
openssl rand -hex 32
```

The key command intentionally prints the pair to **your terminal** for copying into the hosting environment. Do not paste private keys/service-role keys into chat, SQL scripts, screenshots or commits. No production keys were generated or saved by this release.

**Redeploy after setting the variables.** VAPID keys must stay stable between deployments; replacing them requires devices to enable push again. The public key is served by `/api/push/config`; private keys are never returned.

## 3. Automatic execution in Supabase

The scheduler can run in Supabase, including when the Vercel site has no open visitor. It does not require Vercel Cron or a paid Vercel cron frequency.

In **Supabase → Vault**, create:

- `myroster_push_url`: the full production URL ending in `/api/push/dispatch`. For the domain currently in this repository, that would be `https://my-roaster-ten.vercel.app/api/push/dispatch`; use your actual current production domain.
- `myroster_push_token`: exactly the `PUSH_CRON_SECRET` value configured on the server.

Run [`supabase/push-scheduler.sql`](../supabase/push-scheduler.sql) in the SQL Editor. It enables `pg_cron`/`pg_net` and schedules an authenticated request every minute. It checks that the Vault entries exist and replaces an earlier job of the same name. Supabase extension availability/permissions and project uptime still apply.

After 1–2 minutes, verify:

```sql
select * from public.push_dispatch_state;
select jobname, active, schedule
from cron.job
where jobname = 'myroster-push-every-minute';
select status_code, created
from net._http_response
order by created desc
limit 5;
```

A recent `last_success_at` plus HTTP 200 confirms a successful dispatch cycle. A cron job marked successful only confirms the request was queued; inspect the HTTP response and heartbeat too. The profile warns if no successful heartbeat exists in the last five minutes.

To stop scheduled notifications:

```sql
select cron.unschedule('myroster-push-every-minute');
```

## 4. Device test

1. Sign in to MyRoster over HTTPS.
2. On iPhone/iPad, use iOS/iPadOS 16.4+ and add the site to the Home Screen from Safari. Open it from that icon.
3. Open Profile → Notifications. Choose alerts and tap Enable on this device. Only this explicit action requests native permission.
4. Accept the system prompt. If previously blocked, change the browser/OS notification settings; the website cannot force the prompt to reappear.
5. Tap Send test notification (limited to one claim per device per minute). Verify it in system notifications.
6. Close the site, keep the device online and wait for a scheduled booking's next reminder. The account booking must have synced successfully to Supabase. Confirm scheduler health first.
7. Verify that turning off the device subscription stops alerts. Repeat setup separately on another device if wanted.

Preferences apply to scheduled-flight alerts: check-in (-60 min), boarding (-30 min), scheduled departure, delay (+25 min without takeoff), cancellation (+3 hours without takeoff). Save preferences to apply changes and the current interface language to this device. In-flight step/cabin announcements are the existing separate page feature.

## Delivery behavior and limits

- There are no automatic permission prompts when loading the site or scheduling a flight. Declining leaves the rest of MyRoster usable.
- The service worker handles push and notification clicks only. It does not cache pages, intercept fetches or change existing globe/live network behavior.
- The server reads account bookings independently of the browser. It selects only the current reminder stage, not a backlog of outdated boarding/check-in messages. Cancellation catch-up is limited to 24 hours after departure.
- Each subscription, booking, departure time and stage has a database claim. Claims check the latest booking and saved preference before sending, so stale schedules, actual takeoffs and manual cancellations are rejected. Rescheduling creates a fresh reminder generation. Automatic cancellation is distinguished from a manual cancellation.
- Failed sends can retry after a two-minute lease, up to five attempts; HTTP 404/410 removes expired subscriptions. Transient retries and exceptional receipt failures cannot provide a mathematical exactly-once delivery guarantee; stable notification tags reduce duplicates.
- Up to 40 least-recently-checked devices are considered per invocation, with four workers and a roughly 40-second work budget. Larger installations need monitoring and more dispatcher capacity; a healthy heartbeat is not proof that every device received its message.
- Notification lifetime at the push provider is five minutes. Network loss, battery policy, browser restrictions, Focus modes and OS settings may delay or suppress display. A provider-accepted test is not a receipt from the user's screen.
- Signing out unsubscribes this browser and clears its worker account association. A different signed-in account cannot receive notifications intended for the previous account. Other devices remain independent.
- The development environment had no production hosting/Supabase administrative credentials, so production migration, variables, cron and actual Apple delivery require the operator steps above. No real user push was sent during implementation.

## Validation

- 109 automated tests passed, including Web Push request encryption, authenticated endpoint rejection, expiry/retry behavior, worker account isolation and actual PostgreSQL execution of the migration/claim function using PGlite.
- PostgreSQL tests confirm repeatable migration, delivery leases, preference/takeoff/reschedule guards, service-only permissions and the scheduler SQL with simulated Vault/cron functions. Production Supabase extension installation is an operator step.
- TypeScript checked separately with `tsc --noEmit --incremental false`; production build passed. Existing Next build warnings about local Supabase variables and SQLite tracing remain.
- Chromium verified the mobile preference flow using a simulated account and subscription provider. The actual service worker also displayed a notification from a DevTools-simulated push after every MyRoster page was closed. This verifies worker reception/display, not production Apple/provider delivery.
